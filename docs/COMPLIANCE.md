# Compliance Center

Code: `modules/compliance/` (`@founderos/compliance`), shell admin API: `shell/src/app/api/admin/compliance/`. Written from the code on 2026-10-03. The module README is `modules/compliance/README.md`. Spec sections 20-24 and 62.

The Compliance Center is a **checklist to verify at the source, not legal advice**. It tells a business which obligations may apply to its profile and where the official source is. It does not file anything, calculate anything, or say that a business is compliant.

## How it works
1. **Rules** are data: an id, a version, conditions on the business profile, a source (title, URL, date the URL was last loaded), optional recurrence, optional fixed deadline, wording, priority and category. Seed rules live in code (`src/seed.ts`, `RULES_VERSION = "2026-10-03.1"`); admin-managed rules live in two platform tables (below).
2. **Engine** (`src/engine.ts`, pure functions): evaluates each condition as yes, no or unknown against `ctx.business`. Condition types: `country`, `state`, `entity`, `stage`, `flag` (an `operations` yes/no answer), `employees`, `industry`, `industryKnown` and `anyOf` (nesting). Any "no" hides the rule. Unknown profile data, or a rule marked `alwaysCautious`, switches the wording to "Review whether ..." so the tool never says "you must" about something it cannot know. A built-in validator rejects assertive wording ("you must", "is required", "illegal") in cautious rules.
3. **Checklist** (`compliance_items`, business-scoped) is generated by `POST sync` and by every page visit for users who can write. Sync is idempotent (unique per business and rule), never recreates an item marked not applicable, refreshes the wording when a rule's version changes, and deletes only untouched items whose rule no longer applies. The user can add custom items, mark status (`complete`, `attention`, `missing`, `not_applicable`), set their own due dates and renew recurring items.
4. **Publishing to the rest of the product:** `facts` (counts, overdue, next due date, categories missing), `describe`, `attention` (overdue, due within 30 days, marked attention, high-priority items still unconfirmed) and `resolve`/`search`. Business Health and the dashboard read these; the scheduler's `compliance-due-30` and `compliance-overdue` automations create notifications from the attention items (docs/NOTIFICATIONS.md).

## Seed rules and their sources
* **Federal (21 rules):** EIN, income tax return for the business structure, estimated taxes, S corporation election, federal payroll taxes, W-4, I-9, state employer taxes, 1099-NEC, worker classification, BOI reporting status check, licenses and permits, registered agent, trade name (DBA), insurance, sales tax, multistate sales tax, website privacy, cybersecurity, PCI, and industry-specific licensing. Sources are IRS, SBA, USCIS and similar official pages.
* **State (51 jurisdictions, two rules each = 102):** registration with the state, and the annual or periodic report, pointing at each state's official business-filing portal (`src/states.ts`: the 50 states and DC). Together with the federal rules the seed has 123 rules (counted by running the module).
* **Verification status.** Every source URL was loaded on **2026-10-03** (`VERIFIED_ON`). Eight state portals (AK, IL, MA, MN, MS, NH, NY, OH: bot protection, timeouts or challenge redirects) could not be loaded automatically; they are flagged `verified: false` and shown to users as "confirm at source". "Loaded" means the URL answered, not that someone read the page and confirmed the rule's wording is still right.
* **Nothing specific is invented.** No fees, thresholds or due dates appear in the seed rules because none were verified at the source; users set their own due dates. A rule's `deadline` field exists but only for a date a source states, and the seed leaves it empty.
* Coverage limits: US only; no local (city or county) rules; no state sales-tax or state payroll portals per state; no non-US rules; no filing.

## Admin-managed rules
This exists in `modules/compliance` as of the time of reading (`admin-rules.ts`, `rule-schema.ts`, `admin-migration.ts`, `source-check.ts`, `samples.ts`) with an admin API in the shell (`/api/admin/compliance`). Platform admins (the LegalAI `admin` role, same guard as the rest of `/admin`) can add rules without a code change.

* **Storage.** Migration `0002_admin_rules` creates `compliance_admin_rules` and `compliance_admin_rule_versions`. These two tables are the single exception to the "every table has `business_id`" convention: they hold platform-wide content, never business data, and businesses never read or write them directly (the sync reads published rows).
* **Lifecycle.** `draft` to `published`, and `published` to `disabled` and back. Only rules that are published and enabled reach businesses (`loadPublishedRules`); a stored row that fails validation is skipped rather than breaking the sync. Rule ids become `admin:<slug>`. Editing a published or disabled rule bumps its version, which refreshes the wording on untouched checklist items; disabling removes untouched items that came only from that rule. Every change writes a snapshot, and any earlier version can be restored as a new version (history is never rewritten).
* **Validation.** The condition language is exactly the engine's, checked with zod (at most 12 conditions, nesting depth 3, state conditions must be two-letter US codes). To publish, a rule needs an https source URL (no credentials), a source title, a last-verified date that is not in the future, recommendation wording, at least one condition (a rule with none would apply to everyone) and it must pass the engine's own wording checks.
* **Source checks.** An admin can trigger a source health check for a rule: https on the default port only, one checked DNS answer, private and reserved addresses refused, every redirect hop re-checked (maximum 3), 10 second limit, body never downloaded, only the status line and headers. It records what the server answered and where the URL ended up; it does not decide whether the page still says what the rule says, so a person has to read it. It is admin-triggered only, never automatic.
* **Staleness.** A "stale queue" lists seed and admin rules whose last-verified date is older than 180 days (`STALE_DAYS`).
* **Preview.** A preview endpoint shows which of a set of invented sample businesses a draft rule would apply to (`samples.ts`: for example an NC LLC with employees, a Texas sole proprietor with contractors, a California S corporation restaurant). They are not real businesses.
* **Audit.** The module functions take an actor id and leave the audit event to the caller, the shell's admin API.
* **Admin UI.** `shell/src/app/admin/compliance/` exists (a list page, a `new` page and `[id]` pages) alongside the API routes. docs/ADMIN.md is the reference for the admin portal. Pending / not seen: whether any admin rule has actually been published on the live service, and the exact request shapes of the endpoints (they are in `shell/src/app/api/admin/compliance/_lib.ts`).

## Knowledge-source policy
A rule goes in (seed or admin) only if all of these hold:
1. **Official source.** It points to a government or other official page (IRS, SBA, USCIS, a state agency). Not a blog, vendor or law-firm summary.
2. **Loaded and dated.** Someone loaded the URL and recorded the date in `lastVerified`. Re-check periodically; the stale queue flags anything past 180 days. A source that could not be loaded is kept only with `verified: false` and shown as "confirm at source".
3. **No unverified specifics.** Never state a fee, a due date or a threshold that was not read at the source; send the user to the source instead.
4. **Cautious wording where applicability depends on facts we do not hold.** Use `alwaysCautious` and "Review whether ..."; never "you must".
5. **Versioned.** Change `RULES_VERSION` and the rule's `version` whenever the text changes, so existing checklists refresh.
6. **Not advice.** The UI says the list is a starting point to verify at the source and that FounderOS is not a law or accounting firm.

## API (`/api/tools/compliance/...`)
`GET items?status=&category=`, `POST sync`, `GET rules` (version, total and admin-rule counts, which rules apply and how certain), `POST items` (custom item), `PATCH items/:id`, `POST items/:id/renew`, `DELETE items/:id` (custom items only). Writes need a non-viewer role. The admin API is `/api/admin/compliance` (list, preview) with `[id]` and `[id]/<publish|disable|restore|verify|check>`.

## Not built
Per-business rule edits (rule wording changes through code or the admin rules), local and non-US rules, filings and fee calculation, notifications beyond the dashboard and the two scheduler automations,. Tests: `npx vitest run modules/compliance` (needs the local `founderos_test` Postgres).
