# Compliance Center (`compliance`)

Tracks business obligations and deadlines from a configurable, versioned rule set. It is a checklist to verify at the source, not legal advice.

## How it works
- **Rules** live in code, not in the database (`src/seed.ts`, version `RULES_VERSION`). A rule has conditions on the business profile, a source (title, URL, date the URL was last loaded), an optional recurrence and an optional fixed deadline.
- **Engine** (`src/engine.ts`, pure functions): evaluates conditions (yes / no / unknown) against `ctx.business`. Any "no" hides the rule. Unknown profile data, or a rule marked `alwaysCautious`, switches the wording to "Review whether ...".
- **Checklist** (`compliance_items`) is generated by `POST sync` and by every page visit for users who can write. Sync is idempotent (unique per business + rule), never recreates an item marked not applicable, refreshes wording when a rule version changes, and deletes only untouched items whose rule no longer applies.

## Tables
`compliance_items` (business-scoped): rule_id (null for custom), title, description, recommendation, category, status (`complete|attention|missing|not_applicable`), due_date, recurring, recurrence, source_url, source_title, last_verified, completed_at, notes, priority, uncertain, user_edited. Links to other records use the shared links feature (`LinkedItems`).

## API (`/api/tools/compliance/...`)
`GET items?status=&category=`, `POST sync`, `GET rules`, `POST items` (custom), `PATCH items/:id`, `POST items/:id/renew` (next cycle for recurring items), `DELETE items/:id` (custom items only).

## Publishes
- `facts`: `{ itemCount, openItems, overdue, dueSoon, complete, missing, attention, nextDueDate, categoriesMissing }`
- `describe`: counts, overdue, next deadline, unconfirmed areas (<= 600 chars)
- `attention`: overdue (high), due within 30 days (review), marked attention, high-priority items still unconfirmed (review)
- `resolve` / `search`: checklist items, href `/app/t/compliance/i/<id>`

## Admin-managed rules (platform admins only)
Besides the code seed rules, platform admins can add global rules under `/admin/compliance` (spec 45 Compliance Rules, spec 62 Knowledge Sources). The nav link lives in the admin layout.
- **Tables** (migration `0002_admin_rules`): `compliance_admin_rules` and `compliance_admin_rule_versions`. These are the ONE exception to the `business_id` rule: platform content, never business data. Businesses never read or write them directly; they are skipped by per-business export and deletion because they hold no business data.
- **Rule shape** is the engine's `Rule` (same conditions, wording, recurrence, deadline). Conditions are validated with a zod schema for the engine's own `Condition` type (`src/rule-schema.ts`); `state` conditions take a two-letter code, `anyOf` nests three levels, at most 12 conditions. Ids are slugs, namespaced `admin:<slug>` in checklists so they never collide with seed rules.
- **Lifecycle**: `draft` (reaches nobody) -> `published` <-> `disabled`. Publishing needs an https source URL, a source title, a last-verified date (not in the future), wording, and at least one condition; a published rule cannot be edited into an incomplete state.
- **Merge**: the checklist sync (`syncChecklist`) evaluates seed rules plus published admin rules. Editing a published or disabled rule bumps its version, so the existing wording-refresh path updates untouched items (status, notes, due dates are never touched). Re-publishing after a disable is a new version. Disabling a rule (or conditions that stop matching) removes only untouched `missing` items that came from it; anything a person touched stays. Items are always inserted per business: a global rule applies to every business at its next sync, but each item is that business's own row. A stored row that no longer validates is skipped, not fatal.
- **Versions**: every create, edit, publish, disable, restore and verify writes a snapshot. Restore re-applies an old snapshot as a NEW version (history is never rewritten).
- **Preview**: the editor evaluates unsaved content against six invented sample businesses (`src/samples.ts`) with the real engine, showing certain / uncertain / not applicable.
- **Stale queue** (spec 62): seed and admin rules whose last-verified date is older than 180 days or missing, oldest first. Admin rules have "Mark verified today" (a new version, so the date reaches checklist items); seed rules are report-only because they live in code (`seed.ts`, update after re-reading the source).
- **Source health check** (`src/source-check.ts`, admin-triggered only, never scheduled): fetches the rule's source URL server-side over https only (no private/loopback/metadata addresses, DNS resolved once and pinned, re-checked on every redirect, max 3 redirects, 10 s total, body never downloaded) and records HTTP status, final URL and a note on the rule. It reports what the server answered. It cannot tell whether the page still says what the rule says: a person must read it. Many government sites block automated requests (403/429), so a failed check is a prompt to look, not proof the link is dead.
- **API** (shell, platform admin only, audited with `recordAudit`, actions `admin.compliance.rule.*`): `GET/POST /api/admin/compliance`, `GET/PATCH /api/admin/compliance/<slug>`, `POST /api/admin/compliance/<slug>/<publish|disable|restore|verify|check>`, `POST /api/admin/compliance/preview`. Logic is in `shell/src/app/api/admin/compliance/_lib.ts`.
- **Honest limits**: the condition editor takes JSON (with templates to append), not a point-and-click builder; one admin edit is last-write-wins (no edit locking); published changes reach a business at its next sync (page visit or `POST sync`), not instantly; admin content is only as good as the person who sourced it, which is why a source and a verification date are mandatory.

## Seed rules and sources
Federal: EIN, income tax return, estimated taxes, S corp election, payroll taxes, W-4, I-9, state employer taxes, 1099-NEC, worker classification, BOI status check, licenses, registered agent, DBA, insurance, sales tax, privacy, cybersecurity, PCI, industry licensing. Per state (50 + DC): registration with the state, annual or periodic report.
Every source URL was loaded on 2026-10-03. Eight state portals (AK, IL, MA, MN, MS, NH, NY, OH; bot protection, timeouts or challenge redirects) could not be loaded automatically; they are flagged `verified: false` in `src/states.ts` and shown as "confirm at source".

## Deliberately not built
- No specific fees, thresholds or due dates in the seed rules (none were verified at source). Users set their own due dates.
- No state sales-tax or state payroll portals per state, no local (city/county) rules, no non-US rules.
- No notifications beyond the dashboard `attention()` list.
- No per-business custom rules: rules are global and apply to businesses by their profile. A business can add its own checklist items, not rules.
- No non-US (or local) rules unless a platform admin adds them, each with its own source and verification date.
